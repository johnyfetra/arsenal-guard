## Le probleme n est pas seulement technique

Un bug de production a un cout visible: incident, correctif, communication, parfois geste commercial. Un test flaky est plus discret. Il passe le lundi, casse le mardi, repasse apres relance et laisse l equipe avec une question toxique: faut-il croire la CI ?

Quand cette question s installe, la suite de tests cesse d etre un filet de securite. Elle devient un bruit de fond. Les developpeurs relancent les jobs, les reviewers ignorent les signaux, les product managers voient les releases glisser sans raison claire. C est souvent plus cher qu un bug isole, parce que le cout se repete a chaque livraison.

## Le vrai cout d un test instable

Le premier cout est le temps humain. Dix minutes perdues par pipeline semblent acceptables. Multipliees par plusieurs pull requests, plusieurs developpeurs et plusieurs semaines, elles deviennent une dette operationnelle.

Le deuxieme cout est la perte de confiance. Un test fiable qui casse provoque une investigation. Un test flaky qui casse provoque une relance. Cette difference est enorme: elle transforme un signal qualite en routine administrative.

Le troisieme cout est le risque produit. Plus une equipe ignore les tests, plus elle augmente la probabilite de laisser passer une vraie regression. Le test flaky ne cache pas seulement son propre probleme; il diminue la credibilite de toute la suite.

## Les causes les plus frequentes

La plupart des flakies viennent de causes connues: attentes implicites, selecteurs fragiles, donnees partagees, dependances reseau non maitrisees, animations, jobs CI sous-dimensionnes ou absence d isolation entre scenarios.

Dans Cypress comme dans Playwright, la solution n est pas de multiplier les sleeps. Attendre arbitrairement trois secondes peut masquer le symptome, mais cela ralentit la suite et ne garantit rien. La bonne approche consiste a attendre un etat observable: un element disponible, une requete terminee, une donnee creee, une URL stabilisee, un evenement metier visible.

## Stabiliser sans tout jeter

Une stabilisation efficace commence par le classement. Quels tests cassent le plus souvent ? Sur quels navigateurs ? Apres quels changements ? Dans quelle etape CI ? Sans ce tri, l equipe risque de corriger au hasard.

Ensuite, il faut isoler les parcours critiques. Un test de paiement, de connexion ou de creation de compte n a pas le meme niveau de criticite qu un test de filtre secondaire. Les premiers doivent etre traites comme une infrastructure produit.

Enfin, il faut nettoyer les fondations: factories de donnees, fixtures lisibles, selecteurs stables, reset et seed d environnement, retries limites et reporting exploitable.

## Les bons indicateurs

Un taux de pass global ne suffit pas. Suivez la frequence de relance, le temps moyen de diagnostic, les tests les plus instables, le temps de pipeline et le nombre de regressions detectees avant production.

Ces indicateurs permettent de parler le langage business. Un test stable n est pas un luxe technique: c est une reduction du risque et du temps perdu.

## Conclusion

Les tests flaky coutent cher parce qu ils attaquent la confiance. La bonne nouvelle, c est qu une suite instable peut souvent etre sauvee sans refonte complete. Il faut auditer, prioriser, stabiliser les causes racines et remettre la CI au service des decisions release.
